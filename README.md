# Legal Intelligence Research & ML Platform

A research-engineering study of how to classify, extract structured information
from, and retrieve documents in a large legal corpus — using classical ML,
probabilistic methods, traditional NLP, and modern retrieval.

This is not a RAG chatbot. The output is experiments, metrics, and evidence-based
decisions; the production API exists to prove the winning methods can be deployed.

## Rules of the project

1. **Every component needs a reason.** If a model, database, or algorithm cannot
   answer "what problem does this solve, and why is it better here than the
   alternative?", it does not go in.
2. **The test split is opened once**, after experiments are frozen. All design
   decisions are made on `dev`.
3. **Equal tuning budgets.** Every classifier gets the same number of candidate
   configurations. Unequal budgets measure effort, not model quality.
4. **No claim without a significance test.** A gap of 0.807 → 0.812 is reported as
   noise unless a paired test says otherwise.
5. **No hand-typed numbers.** Every table below is regenerated by `make report`
   from `results/*.json`.

## Splits

Four-way, group-aware: `train / dev / calib / test`.

- **Group-aware** — near-duplicate clusters (MinHash + LSH) never straddle a
  boundary. Legal text is boilerplate-heavy, so a naive random split leaks
  near-identical documents across train and test and inflates every metric.
  Both naive and deduplicated numbers are reported; the gap is a finding.
- **`calib` is separate from `dev`** — calibration fit on the split used for model
  selection is contaminated calibration.
- **Temporal mode** — train on older documents, test on newer, to measure drift
  rather than assume it away.

## Tracks

| Track | Question | Key outputs |
|---|---|---|
| A — Supervised ML | Is a complex model necessary, or does a linear/probabilistic method suffice? | Classifier benchmark, calibration, bootstrap CIs, temporal robustness |
| B — Retrieval & scale | Does hybrid retrieval actually beat BM25 and dense alone on legal queries? | BM25 / dense / RRF benchmark, chunking study, Dask scaling curve, latency & index cost |
| C — NLP / IE | Where does a general-purpose NER model fail on legal entities, and what fixes it? | spaCy baseline vs domain rules, entity-level P/R/F1, error taxonomy |

The production layer consumes the **winner of each study**, not every model built.

## Milestone 1 (build this before anything else)

5K documents → dedup → fixed split → TF-IDF + Logistic Regression → BM25 →
evaluation script → FastAPI → Docker.

```bash
make install
make data          # ingest -> dedup -> split
make experiments   # writes results/*.json
make report        # regenerates the decision table
make test
docker compose up
```

Only after that runs end to end do the serious experiments get added, one at a time.

## Decision table

Generated into `README_RESULTS.md` by `make report`. Every row: methods tested,
metric, winner, margin, and whether the margin is significant.

## Limitations

- Retrieval relevance judgments are partly **derived from citation structure**,
  not human assessors. Citation ≠ relevance; this biases toward
  precedent-heavy queries and is the weakest assumption in the project.
- Dask scaling here is **multi-process on one machine**, not distributed
  computing across a cluster. The scaling curve and its flattening point are the
  interesting part; the claim stops there.
- Legal NER labels are partly rule-derived and imperfect.
- Temporal and jurisdictional coverage is limited by the public datasets used.
- This is an **experimental research system, not legal advice.**
